# Heavy-route workflow (Stage 0-5)

> Only read this when a target actually escalates past the Fast path (packed/protected/stalled -- see SKILL.md's escalation triggers). The fast path *is* a compressed pass through these stages; drop in at whatever stage the blocker demands.

- **Stage 0 -- Kickoff**: get the absolute path. If you hit a missing non-GUI tool, run `bootstrap-tools.ps1` (health-check) to see what's missing, then present the tool + source and let the user install (hard stop 2). Native target -> confirm IDA is available up front so static+xref is first-class from the start.
  - **[STARTUP] The anchor only auto-loads if Codex was started with its working directory INSIDE the target's project.** If the session was launched elsewhere (e.g. the skill dir), tell the user once: "为让进度/壳信息压缩后不丢,请在【目标程序所在目录】启动 Codex" -- then still create the anchor there for the next session.
  - **[ANCHOR -- already created as the FIRST ACTION above, unconditionally, the moment you had the target path] `AGENTS.md` in the TARGET's own directory** (project-scoped, one per target, no cross-contamination) from `templates/target-agents-md-template.md`. It is **auto-reloaded into context every turn (so it survives context compaction)** -- pinning "obey xiaotao-win-flow + the scan.ps1 shell-layer map + a pointer to re-read `<target>-attempts.md`", the fix for the post-mortem failure "after compaction, forgot the shell info and stopped following the skill" (Rule 7). Created as a skeleton first; **populate the shell-layer map after scan and progress as you go** (real evidence only, not a guess -- Rule 6). Keep step-by-step detail in `<target>-attempts.md`. Re-read this anchor + attempts.md before every action, especially right after a compaction.
    - **[MUST FILL] Put THIS skill's absolute path into the anchor** (both the "第一件事" reactivation block and 目标基本信息). After a disconnect/interrupt/new session, SKILL.md may be out of context but the anchor is auto-loaded -- so the anchor's first instruction is "confirm xiaotao-win-flow is active; if not, re-invoke `$xiaotao-win-flow` or read `<skill-path>/SKILL.md`, then re-read this file + attempts.md". This *instructs* reactivation (raises the odds), it is not a mechanical auto-load; the anchor's compressed core rules are the fallback if the full skill isn't reloaded.
  - **Heavy route only**: copy `attempts-log-template.md` to `<target>-attempts.md`, reconcile disk vs log, draw a read-only trust-boundary map.
- **Stage 1 -- Packer + bitness + triage**: `scripts/scan.ps1 -Target <path>`. Read (a) bitness (PE32->x32dbg, PE32+->x64dbg); (b) **mandatory** classification via `triage-router.md` -- misclassifying Nuitka/Go/.NET-AOT derails everything; (c) packer tier -- **packed -> search the shell online first (Rule 3)** -> `hard-target-playbook.md` L1/L2/L3 -> re-triage. Installers (Inno/NSIS/MSI) get their internal program extracted first. Kick off `env-recon.md` in parallel.
- **Stage 2 -- User runs target under debugger + captures** (user personally, Rules 8/9): start Reqable/proxy *before* the target. Confirm the Reqable MCP. Wait for explicit user confirmation before continuing.
- **Stage 2.5 -- Route planning (mandatory, Rule 16)**: resolve the control-ownership fork (Rule 28) first -- can-inject -> Hook routes rank above capture as a class; can't -> capture/fake-server rank up. Then classify the auth arch (`auth-arch-classify.md`). List >=2-3 candidate routes, score feasibility/difficulty, filter by env-recon + `scan.ps1` step [4]. Hard veto: "core heavily protected" drops "fake the server".

   | Candidate | Evidence | Score | Difficulty | Priority |
   |---|---|---|---|---|
   | Fake the server | verification request, proxied, replayable | | | |
   | Local state/file forgery | auth lands in a local cache | | | |
   | Memory/hook decision point | plaintext model, local compute | | | |
   | Read source / recover symbols | bytecode/Nuitka/Go per triage | | | |

- **Stage 3 -- Fake the server** (only if scored highest; skipped if "core heavily protected"): first check per `auth-arch-classify.md` whether the client can even be bypassed. Forge **every** token-gated endpoint in one pass; `[Y]` UI-unlock vs `[OK]` feature-verified, only `[OK]` proceeds; encryption -> passive-observe->offline-verify->forge (Rule 19) with all crypto libs hooked at once (Rule 20).
- **Stage 4 -- Deep analysis** (only if Stage 3 didn't pan out): .NET IL -> `tool-registry.md Sec.5`; junk/CFF/VM -> Frida Stalker to bypass or `deobfuscation-playbook.md` for the algorithm. **Verdict inside the VM'd core -> Rule 27 governs (hook the boundary, don't bounce to fake-server).**
  - **Target the right module, not reflexively the exe (Rule 13)**: point IDA at the auth-carrying DLL/pyd itself, or attach x64dbg and `bp` its named export -- the exe is often just the launcher.
  - **4A static**: user opens IDA (Rule 8); `references/ida-re/SKILL.md`; Nuitka -> `playbooks/nuitka.md`; Go/Rust/Flutter/Unity -> `tool-registry.md Sec.5.7`.
  - **4B dynamic**: user opens debugger/target (Rule 8). x64dbg (state-snapshot/diff/tracealyzer/find-oep, break before the final compare and dump the computed value) / Frida (`references/frida-win/SKILL.md`, hook everything at once) / angr for purely-local checks.
  - Anti-detection: `hard-target-playbook.md` Sec.2. Modifying local auth-state needs consent+backup (Rule 5).
- **Stage 5 -- Reverse into hardening**: from `[OK]` points only (Rule 6). Per point, cross-reference `auth-bypass-cheatsheet.md`, prioritize weak->strong. Deliver `{bypass -> location -> hardening}`, one-to-one.
