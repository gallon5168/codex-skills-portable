# Iron Rules -- full write-up (30 rules)

> `SKILL.md` keeps a one-line checklist per rule; this file has the full rationale + pitfall history. On conflict, this file wins.

**Coverage calibration -- know where these rules are battle-tested vs thin, so you don't over-apply them.** The heavy-route rules (esp. 14/16/26/27) are distilled mainly from **one hard case**: commercial VM/packer shells (VMProtect/Safengine/Themida) + compiled Python (Nuitka/PyArmor) + WebView/Tauri + PyInstaller. On those, apply them with confidence. **Thinner / unvalidated by a real case here**: pure .NET commercial obfuscation (Sec.5 tools exist but the *posture* is VM-centric), pure network-protocol RE without a rich local client, license-algorithm/keygen work (angr/symbolic path is registered, not battle-tested). **Out of scope**: Android/APK, mobile, non-Windows. **Rule when off the well-trodden line**: your priors are weaker there -- lean *harder* on Rule 3 (search this exact target class + forums 看雪/52pojie/GitHub *before* acting) and don't reflexively force the VM/packer mental model (e.g. don't assume "auth is in the VM" on a .NET target, don't jump to boundary-hook on a plain network gate). Match the method to what the target *is*, per `triage-router.md`; the rules are heuristics from one lineage, not universal law.

---

1. **Confirm the MCP tool actually exists before using it, by real name, not the name a doc happens to use**: before calling any Reqable/IDA/x64dbg MCP tool, confirm it's installed -- if not, stop and ask the user to install it, don't improvise a substitute. A sub-skill doc's tool names (e.g. `references/x64dbg/*/SKILL.md`) may not match what's actually connected this session (different MCP implementations vary in prefixes/methods -- one might lack batch-trace and only offer step-by-step). Verify the referenced tool name exists in the current tool list before following a sub-skill's steps; if it doesn't match, use that doc's missing-tool fallback or skip to an alternate route (Rule 14).

2. **Web lookups route by destination -- overseas via proxy, domestic direct; no blind port scanning**: run `scripts/netcheck.ps1`, which reports two verdicts.
    - **Overseas (GitHub tool/repo lookups, Google): proxy-first.** It auto-detects the system proxy (registry HKCU Internet Settings) and prefers routing through it; only when no proxy is configured does it fall back to direct. Two stop-and-ask cases: (a) proxy configured but unreachable (`OVERSEAS=PROXY_DOWN`) -- almost always the 科学上网 tool (VPN/Clash/v2ray) isn't running; tell the user to start it and retry; (b) no proxy and direct also fails (`OVERSEAS=NO_NETWORK`) -- tell the user to start the 科学上网 tool **and** set the system proxy. Rationale: behind the GFW, direct connections to github/google are polluted or time out, so proxy-first gets complete results and successful tool downloads.
    - **Domestic CN RE forums (看雪 `bbs.kanxue.com`, 吾爱破解 `52pojie.cn`): direct, NOT through the proxy, and prefer `curl.exe`.** Verified fact (curl.exe test): both return 200 on a direct connection but fail the TLS handshake through an overseas proxy exit IP (`schannel: failed to receive handshake`) -- so forcing them through the 科学上网 proxy *breaks* them. Also, PowerShell's `Invoke-WebRequest`/.NET TLS stack fails their handshake even direct; use `curl.exe` (schannel) instead. `netcheck.ps1` probes this as `DOMESTIC=DIRECT_OK`. **Never send a domestic RE forum through the proxy.** (Scope: EXE/PE targets only -- these two are the PE-unpacking boards; Android/APK forums are out of scope.)

3. **Pick the best tool per target, never settle for whatever's local; and for any packed/protected target, SEARCH the specific shell online BEFORE acting**: check `references/tool-registry.md` first for the tool best suited to *this* target (don't force an old local `uncompyle6` onto newer Python, or an x86 decompiler onto .NET) -- "the user already has X" is never a reason to use X over the more suitable tool. If the best tool isn't installed, **do not auto-install it**: name it + its source and stop for the user to install (Rule 5; `fetch-tool.ps1 -Probe` only *probes aliveness and prints the install command / download link*, it never installs). If not in the table, search "how to handle **this packer/protector/version**," never "crack this software"; for an algorithm like RSA/AES, search for a third-party library implementation, not a crack. Add anything better found this way back into tool-registry.
    - **[SCAN ALL MODULES] Check the exe AND every same-dir dll/pyd for a shell, in one pass -- the shell is frequently on an SDK DLL, not the main exe.** `scan.ps1 [P]` now maps every module's shell automatically; read that map. A real run wasted many rounds scanning only the main exe (which was clean) before finding the Safengine shell sat on `SPCloud64_Py.dll`. Which module is packed decides what you attack -- go at the **packed layer**, don't default to the main program.
    - **[HARD GATE] Packed/protected shell -> the FIRST action is a targeted web search, not a probe.** The moment `scan.ps1` identifies a real shell (Safengine / VMProtect / Themida / Enigma / ASProtect / PyArmor / any commercial protector) with a version -- on the exe OR any module -- you MUST look it up online first -- 看雪 `bbs.kanxue.com` / 吾爱 `52pojie.cn` (direct, per Rule 2) + GitHub/issues (proxy, per Rule 2) -- for that **exact shell + version's** documented unpack / devirt / anti-debug-config technique, BEFORE any write-op on the target (no inline hook, no byte-patch, no naked debugger, no Pin/tool integration). Rationale (paid for in a real run): un-researched intuition-grinding on a hard shell burns rounds *and* trips its CRC/anti-debug/anti-DBI defenses -- almost every commercial shell has a verified, published method that a 5-minute search finds. Keyword templates: `<shell> <version> 脱壳/反调试/绕过`, `<shell> ScyllaHide 配置`, `<framework> <version> crash/bug`, `<tool> <dependency version> 不兼容`, `<verbatim error text>`. This gate binds together with SKILL.md Fast-path step 2(a) and Stage 1; "I'll just try a hook first" on an un-searched shell is the exact banned move.
    - **Tool version/environment pre-check before heavy integration**: before investing rounds into a fetched tool (compiling it, adapting its project files, wiring a dependency like Intel Pin), first confirm via search + a 5-minute minimal smoke test that this tool's version actually works against *this* shell+version. A real run compiled UnSafengine64 + adapted 4 vcxproj spots + built, only to find Pin 3.31 crashes on that SE shell (the tool was only ever validated on Pin 3.18) -- the "does it even run here" check costs minutes, the blind integration cost many rounds.

4. **"Code exists" != "it's running"**: conclusions need the real call chain / runtime verification. Before marking a critical check point `[OK]`, there must be at least one breakpoint/hook hit with a call stack (or equivalent: an error string traced to a code line, a memory-breakpoint record). Anything only seen in disassembly/strings/decompiled source gets tagged `[static inference only]` -- never mixed with runtime-confirmed evidence in the same breath. Static-first isn't wrong (it's the shortest path for a decompilable managed target); the mistake is skipping the cheap runtime confirmation at the delivery moment and paying for it in rework later.

5. **Get user consent before any change or download.**

6. **Never write hardening without personally witnessing the bypass; attribute causation only after single-variable isolation**: a technique only enters the hardening deliverable once the user has personally watched it succeed (patch really unlocks it, hook really returns authorized, modified response really gets accepted -- reproducible evidence). "Theoretically bypassable" never gets written up, at most it's "pending" in the memory log. If success followed several simultaneous changes (reset a flag + resend a ticket + patch a token), don't attribute it to just one -- retest by undoing each change individually to find which one actually mattered (often only one did; the rest were noise cleanup). When isolation isn't feasible, the hardening doc must say "conjecture, not isolated-verified" -- never write it as settled causation, or you'll harden a mechanism that was never the real bypass.

7. **Log every step immediately, read old logs before trying anything new, tag every claim's confidence**: maintain a memory log per target (`templates/attempts-log-template.md`). Log every attempt right away, success or failure -- especially important after context compaction, defer to the log over memory. But the log is only authoritative once reconciled against disk (Stage 0 step 2) -- if disk has an artifact the log doesn't mention, disk wins until reconciled. Tag every claim: `[OK] verified by an actual run` / `[WARN] conjecture, based on X, unverified` / `[X] disproven`. Never state an unverified guess in the same neutral tone as hard evidence -- a real incident wrote "blocked by `_verify_session_hash`" (guessed from the name) next to "error text = 'session integrity check failed'" (rock-solid) in matching tones, and the guess nearly got carried forward as fact until enumeration disproved it. **Mandatory write-back cadence**: logging-when-you-remember isn't enough -- long sessions silently desync (one real run's attempts.md froze for hours while dumps/extraction/analysis/vectors piled up unlogged). Two hard checkpoints: (a) write that stage's findings back to attempts.md before advancing to the next stage; (b) after every context-compaction recovery, re-run Stage 0's disk-scan reconciliation before continuing.
    - **[ANCHOR] Compaction-surviving state must live in an AUTO-reloaded file, because `attempts.md` is NOT auto-reloaded after compaction.** attempts.md holds full detail but only re-enters context when you deliberately re-read it -- so a compaction can silently drop the shell info and the "obey the skill" framing, which is exactly the post-mortem failure "after compaction, forgot the shell + stopped following skill rules". Fix: **as the unconditional FIRST ACTION -- the instant you have the target's absolute path, before scan/analysis -- create `AGENTS.md` in the TARGET's own directory** (project-scoped, one per target -- no cross-contamination; from `templates/target-agents-md-template.md`). Create it as a **skeleton** first (skill abs-path + re-activate instruction + core rules), then populate the shell-layer map + progress as you discover them. Creating it up front (not "once a shell is found") means a disconnect one turn in still leaves an auto-reloading anchor. Codex auto-injects that file every turn while the working directory is inside the target's project, so it survives compaction. Put in it: (1) a **top "re-activate the skill" instruction** -- after a disconnect/interrupt/new session/compaction, SKILL.md may have dropped out of context while this anchor stayed auto-loaded, so the anchor's first line tells you to confirm xiaotao-win-flow is active and, if not, re-invoke `$xiaotao-win-flow` or read `<skill-abs-path>/SKILL.md` (fill the skill's absolute path in at creation), then re-read this file + attempts.md; (2) "obey xiaotao-win-flow" + the rules most easily forgotten (these are the **fallback core** if the full skill isn't reloaded); (3) the `scan.ps1 [P]` shell-layer map (which module has which shell -- real evidence only, Rule 6); (4) a pointer to re-read `<target>-attempts.md` before acting. **Honest mechanism**: the anchor *instructs* reactivation (raises the odds it happens), it is NOT a mechanical auto-loader for the skill -- which is exactly why (2) carries the compressed core rules as a safety net. Keep detailed flow in attempts.md; keep the durable anchor in `AGENTS.md`. **Never** write a target's shell info into a global `~/AGENTS.md` -- that pollutes unrelated sessions; per-target project scope only.
    - **Leave a trace per step, never delete a disproven entry**: log granularity is every step, not every method -- what was checked, what was concluded, why the next step follows. A disproven method/conclusion is never deleted or rewritten as untried -- append "`[X]` disproven + evidence" after the original. This stops (a) re-walking a known dead end, and (b) mistaking an overturned guess for settled fact. The memory log wants the full trial-and-error history, not a success-only summary -- failed paths are themselves valuable information.

8. **Every open/launch-type tool is opened by the user manually -- never launch it yourself**: Reqable, x64dbg, IDA, **jadx (jadx-gui + MCP plugin)**, Frida's target process, the target software itself -- all stopped-and-user-opens. Continue only once the user confirms it's open, target loaded, MCP/CLI available. When asking the user to open something, give a verified absolute path (e.g. read from the process's main module) -- don't just say "open the target" and leave them guessing which file. Concretely for a GUI-MCP tool (IDA / jadx alike): **stop -> hand the user the exact absolute file path -> the user opens it in the tool -> the user says "opened" -> you confirm the `mcp__*` methods are live (Rule 1) -> only then continue.** Never assume the tool is already open or the file already loaded.

9. **Real interaction with the target software is always done by the user -- never on their behalf**: clicking, typing, triggering features, walking through login/auth flows -- stop and let the user do it, continue once they report the result.

10. **Default single-line output, expand only at key decision points**: don't ask what you can verify yourself; one truly-blocking question per turn max, otherwise just execute. No "here's my plan" preambles, no unused alternatives listed, no restating confirmed facts. A real red team has no insider info and goes straight at the target -- it doesn't keep checking in. Non-critical points (no risk/result/decision) compress to one line or get omitted entirely; only expand for a critical result, a direction change, or a needed decision. In one session the user complained twice about "slow, narrating constantly" before it stuck -- single-line has to be the default, not an aspiration. Same at skill startup: no preamble, no background recap, no plan announcement -- straight into Stage 0.

11. **Decide multiple-choice questions yourself -- don't punt to the user**: any choice settleable from evidence/RE common sense (which bypass route, which hook point, Frida vs x64dbg), weigh it, pick, state why, execute. Only stop for facts that require the user's own GUI action/observation, or high-risk irreversible actions. Default assumption: the target is unactivated with no legitimate license -- don't keep asking, proceed on that basis.
    - **[WARN] Red-team zero-credentials rule (fixed)**: a red team has no correct password, no legitimate account, no valid key -- non-negotiable baseline. Never have the user log in correctly, enter a valid key, or activate first "to see how it works"; never treat "get one successful sample" as a prerequisite. What a red team has: wrong/forged/empty credentials, or self-constructed input. If a step depends on "first get one correct login," that step is wrong -- replace it with: trigger the flow with wrong input, observe the refusal, work backward from there. Even Rule 19's passive-observation sample is captured under the red team's own wrong input, never borrowed correct credentials.

12. **Attribution needs hard evidence -- never guessed from name/adjacency/common sense**: any "this file/process/config belongs to the target" claim needs a file handle the process has open, an absolute path from the process's own memory, a matching timestamp, or a field-for-field structure match. A similar name, adjacent directory, or shared vendor brand is never evidence. If unverified, say so explicitly rather than building on it as fact.
    - **Locating a relative-path file** (source does `open('activation.json')` with no directory): the program reads it relative to its process's real CWD, which isn't necessarily the exe's directory. Hard-evidence method: read the process's PEB (`NtQueryInformationProcess` -> PEB base -> `PEB+0x20` for `ProcessParameters` -> its `CurrentDirectory` UNICODE_STRING at `+0x38` -> `ReadProcessMemory` the buffer) to get the real CWD. This is how one real run confirmed `activation.json` actually landed in `...\Gulang\`, not somewhere assumed. Equally valid: Process Explorer/handle view of open file paths, or a Procmon `CreateFile` event. Don't guess "CWD = wherever the exe is."

13. **IDA=static, x64dbg=dynamic, control x64dbg via attach+commands**: static disassembly/decompilation/xrefs through IDA MCP; dynamic debugging through x64dbg. x64dbg should prefer attaching to a running process over relaunching (plaintext often only exists post-decryption; a restart loses that state). Drive x64dbg via commands/MCP (breakpoints, registers, memory, stepping) without asking the user to click around by hand; only stop for things that need a human (launch/load/GUI interaction, Rules 8/9). Wait for IDA's auto-analysis to finish before doing xrefs, or results are incomplete.
    - **[PICK THE MODULE, DON'T DEFAULT TO THE EXE -- the auth/crypto/license logic is frequently in a DLL/pyd, and analyzing/debugging that module directly is usually easier]**: the main exe is often just a launcher / GUI shell; the real decision logic lives in an SDK/core/plugin DLL (or a `.pyd`). Attacking that module directly is typically *easier* than the exe: it's smaller and focused, its **exports are named entry points** (`verify_/check_/is_licensed/decrypt/...` hand you the function for free -- no hunting in a giant binary), and it sometimes carries **weaker anti-debug** than the launcher. So "what do I point IDA/x64dbg at?" is a **decision**, not automatically the exe.
      - **How to pick the right module (evidence, not name -- Rule 12)**: the module carrying the auth **exports** (dump the export table); the module the exe **imports its check from**; the module that **references the auth strings/APIs** (MessageBox/RegQuery/license text -- xref backward to its module); or the **packed module from `scan.ps1 [P]`** (the shell is usually on the module worth attacking). Confirm it's actually loaded/called by the target (handle/import/call-site), don't assume from a suggestive filename.
      - **[ORDER] Web-search technique FIRST, then decide which module the user opens (Rule 3).** Deciding "open X in IDA / attach x64dbg to module Y" is itself a decision that must be preceded by a search (per Rule 3's search-first mandate) -- look up how this target/module class is analyzed (which module usually holds the auth logic for this framework/SDK, how to load or attach that specific DLL/pyd, whether that module carries its own anti-debug) on 看雪/52pojie/GitHub (Rule 2 routing). Only after that search do you commit to a module and hand the user its exact absolute path (Rule 8). Don't pick the open-target on a hunch, then search afterward -- the search informs the choice, not the other way round.
      - **Static (IDA)**: open the **DLL/pyd itself** as the IDA target -- a focused module with named exports beats disassembling the whole exe. For a reflectively-loaded / unpacked module, dump it first then open (Rule 26).
      - **Dynamic (x64dbg)**: attach to the **running process**, then work in the **target module's address space** -- `bp` on the DLL's export, or break on module-load and set breakpoints once it's mapped; the exe's own entry is irrelevant if the check is in the DLL.
      - **Isolation (exercise one export without the whole app)**: a specific export can sometimes be driven via `rundll32` or a minimal caller harness to hit just that function -- but this **executes DLL code** (DllMain + the export), so it's "running the target": user-driven + consented (Rules 5/8/9), and only when the export is self-contained enough to run standalone.

14. **2 structural-failure signals from junk code/fake call stacks -> switch to Frida trace immediately, no 3rd manual retry**: any of these means the target uses junk code + fake call stack (obfuscator replaced `call` with `push fake_retaddr; jmp`, so there's no real stack frame) -- continuing to manually single-step is burning turns on a structurally dead path, not "using the wrong method":
    - Same-address disassembly keeps misaligning (short-jump chains, an `E9` landing implausibly, `push imm64` bytes misread as an instruction).
    - `step_out`/stack-walk times out twice, or RIP lands somewhere unrelated (message loop, Qt dispatch) instead of the expected caller.
    - A function-boundary lookup for that address returns "not found."
   Once these add to 2 (any mix counts), stop retrying and go straight to **Frida Stalker** (or equivalent in-process trace) to record real execution -- naturally immune to junk code/fake frames, zero MCP round-trips. Confirm CLI/deps per Rule 1 first (`frida --version`; a Python-binding error may be a DLL/interpreter version conflict, not "not installed"). This is a mandatory trigger, not a preference.
   - **[WARN] Stalker is the bypass-oriented default but insufficient when the deliverable needs the algorithm**: it gives real execution flow (enough to patch/observe/bypass) but not the algorithm inside virtualized/flattened code. If the target needs keygen or algorithm-level signature forgery (cheatsheet 4b/6), black-box trace can't solve it -- switch to `deobfuscation-playbook.md` for real deconstruction. Order: black-box if it suffices; deconstruct only if the algorithm itself is required, starting with an off-the-shelf devirtualizer.
   - **Isomorphic signal: "the verification loop is too heavy"**: the same symptom recurring twice, both times answered with a heavyweight "change config + rerun the whole target" loop, is also a structural dead end. On the second occurrence, ask "can a minimal command independent of the target program falsify this" -- almost always yes: `openssl s_client` (`-proxy`) for network/TLS issues, an offline script loopback for crypto issues, `-version`/`--dry-run` for parameter-passing issues. Real lesson: 3 rounds of "change config -> full rerun -> check error" when one `openssl s_client -proxy` call would have pinned the root cause in seconds.

15. **Interpreted/managed packaging (PyInstaller/py2exe/Electron/Java/.NET) goes unpack->de-bytecode/IL->read source; Go/Rust/Flutter/.NET-AOT/Nuitka are natively compiled and do NOT belong here**: once Stage 1 confirms genuine bytecode/managed packaging, native debugging isn't the main route -- source-level logic is fastest. **[WARN]** Go/Rust/Flutter (AOT), .NET NativeAOT, Nuitka/mypyc/Cython compile to native code with no bytecode -- these need native RE + symbol recovery (`tool-registry.md Sec.5.7`; Nuitka specifically -> `playbooks/nuitka.md`), never "unpack->de-bytecode" (Go is especially easy to misjudge -- rich symbols but recovered via moduledata, not de-bytecoding). Using PyInstaller as the worked example (check `tool-registry.md` for the matching tool on other packers):
    - **Unpack**: `pyinstxtractor-ng` (more stable than the old `pyinstxtractor`) -> `<exe>_extracted/` with `.pyc` files and `PYZ-00.pyz`'s modules. Main logic is usually in `<main_name>.pyc` or `_build_*.pyc`.
    - **Decompile pyc->source**: pick the decompiler matching the target's Python version (Rule 3) -- `decompyle3`/`uncompyle6` for <=3.8, `pycdc` for newer; check the pyc magic bytes or `python3XX.dll` to pin the version, fetch from `tool-registry.md Sec.5.5`.
    - **Fallback for newer Python (3.12+) decompilers not caught up** (Py3.14 hit `unhashable type: 'slice'` in uncompyle6/xdis): download the exact-matching official embeddable Python, use its native `marshal.loads(pyc[16:])` + `dis.dis()` to get bytecode -- not source, but `LOAD_GLOBAL`/`LOAD_CONST`/`CALL`/jumps are enough to read the full auth logic (constants often reveal URLs, field names, `'permanent'`/`'expired'` strings directly).
    - **mypyc/Cython C extensions (.pyd/.so)**: already native, no Python source to recover -- switch to black-box testing (change input/local state, observe output; or Frida-hook exports).
    - **Nuitka gets its own dedicated treatment** -- `playbooks/nuitka.md`, don't apply this rule's PyInstaller chain to it.
    - **Enumerate every auth layer, don't stop after the first -- and drive it gate-by-gate (applies to ALL target types, not just interpreted)**: auth is defense-in-depth, not one gate. Targets stack layers in series -- a real run hit (1) a login boolean -> (2) a PIC/machine-code check calling `os._exit(0)` during init -> (3) GUI content gated on init completing; each only surfaced after the previous fell. While reading source / hooking, list *every* gate (every check function, every `expired`/`unauthorized`/`exit` branch, every state file, every second verification: heartbeat, machine-code, integrity self-check). Then **progressive-gate loop**: bypass one -> immediately run a tracer (faulthandler / monkeypatch `os._exit`/`sys.exit`/signal handlers / a logging proxy) to locate the *next* termination/exception point -> bypass that -> repeat until the real feature runs. Witnessed grading: `[gate]` flipped < `[alive]` process survives < `[OK]` feature truly usable -- only `[OK]` is a delivered bypass (Rule 6). Bypassing one layer while others hold leaves the whole thing locked.
    - **[WARN] Symmetric native clause -- native + already-decrypted-in-memory + obfuscated/large-framework goes dump->IDA+xref, NOT hand-driven MCP linear disassembly**: this rule's "read the source" shortcut is for genuine bytecode/managed targets. Its native counterpart is not "single-step in the live process" -- it's **dump the decrypted module -> IDA (recursive-descent disassembly + xref)**. Once a native module is confirmed plaintext in memory (shell self-decrypted, reflectively loaded, or hand-dumped), IDA static + xref is the shortest path to any static fact (a constant, a branch condition, an algorithm shape, who-references-this-string); MCP/x64dbg `disassembly_at` is *linear* disassembly and misreads junk code (`EB 01` skip-bytes, overlapping/fake jumps) into phantom instructions. Don't grind linear reads on an obfuscated native body -- that's the exact failure mode Rule 26 exists to stop.

16. **Lay out a scored route table after static recon, before acting -- not a reactive spot-a-problem-improvise loop**: the moment Stages 1/2 finish, stop and do route planning (Stage 2.5) instead of diving into whichever route feels closest (habitually network forgery). Based on static evidence (assets plaintext locally? auth lands in a local cache/registry? are responses replayable/signed/session-rotated? interpreter-packaged?), list >=2-3 candidate routes, score feasibility+difficulty, rank in the memory log, then work the top one. Static evidence often already points at the answer (a multi-GB plaintext model + local compute screams "memory/hook route beats network forgery") -- don't bury it. When a route stalls, return to the table and decide keep-grinding-or-switch, don't improvise randomly.
    - **[DON'T DODGE THE SHELL -- the auth boundary decides where to unpack, not "avoid the shell"]**: a packed/protected target is never a reason to reach for a "cheaper" route around the shell. **fake-server / passive-capture / patching-outside-the-shell almost never work on real commercial protected software** -- the verdict is *inside*, and the shell is specifically built to defeat those shortcuts. The correct posture: **first locate the license/auth boundary (which module, which check, where the verdict is produced and consumed), and let THAT decide where to unpack (or where to hook the boundary)** -- unpack is *targeted at the auth boundary*, not "strip the outermost layer blindly" and not "skip the shell". Engaging the shell (unpack at the boundary, or black-box the boundary per Rule 27) is the job; dodging it to a softer-looking route is the #1 failure mode. This generalizes the VM veto below to *all* protected targets.
    - **A heavily-protected core vetoes "fake the server"**: when the core is behind a VM-based protector (VMProtect/Themida/Enigma VM/Code Virtualizer) or strong encryption, the scoring step vetoes "fake the server/simulate offline" outright -- heavy protection means the developer already paid to protect the core and won't have left a cheap HTTP-response shortcut; the real decision logic is inside VM bytecode. Public tooling for this category is uniformly head-on attack (NoVmp/MogVMP/titan for devirtualization, unlicense/Magicmida for unpacking, Triton/VMDragonSlayer for symbolic execution) -- none go "around the VM." Once heavy protection is confirmed, the main line is devirtualization/unpacking/symbolic execution (`deobfuscation-playbook.md` Sec.3), don't burn turns on network forgery. **Boundary**: only vetoes VM/strong-encryption; a compression-only packer (UPX/ASPack) unpacks to the plain original, so faking the server remains valid wherever it already was. No conflict with Rule 14 -- Rule 14 objects to hand-single-stepping junk code, and the correct way to attack a VM is exactly Frida Stalker / devirtualizer symbolic execution.

17. **Before dynamic injection, confirm the target isn't in a modal state -- a modal dialog freezes the whole injection channel**: any open dialog (including one you triggered) stalls the Qt/GUI event loop, and a Frida hook on a high-frequency API will never fire -- the single biggest time sink in practice. Before every injection, do a read-only check (enumerate top-level windows, or just ask the user "any dialogs open?"). If the previous injection triggered an error dialog, require the user to close it (or restart the target) before the next attempt.

18. **Grade an unknown function by name prefix before blind-calling to probe params -- action verbs have real side effects**: Cython/compiled builtins have no introspectable signature, so "missing param just errors, errors are safe" doesn't hold -- some functions execute real logic with 0 args (one real run's blind call to `_set_auth_compromised` flipped a live process's circuit-breaker flag). Grade by prefix: `get_`/`is_`/`verify_`/`check_` lean query (safer); `generate_`/`set_`/`refresh_`/`reset_` lean action (side effects). For action-type functions, read the docstring first or skip probing entirely, only calling deliberately when actually needed -- never take on an unknown side effect just to count parameters.

19. **Build a real-response field dictionary before forging anything; encrypted/binary responses go passive-observe->offline-verify->forge, strictly in order**: get at least one real response via read-only means (curl/passive capture) first -- never reverse-engineer a backend field name from a frontend variable name (a real pitfall: guessing `lineId` from a frontend variable, when the real field was different, wasted 2 repackage-restart rounds). A forged response's structure is an exact copy of the real one with only values swapped, not a guessed-plausible structure.
    - **(1) Passive observation**: hook to record only, don't alter flow/return values -- get a complete sample against the real server (request/response plaintext+ciphertext, encryption call params).
    - **(2) Offline verification**: away from the target, script-verify the captured params actually decrypt the known ciphertext -- seconds of cost, catches most misunderstandings.
    - **(3) Then forge**: only after offline verification passes, write the live forged server.
    Evidence tiers: `[R] statically suspicious` (code looks like it, unrun) / `[Y] UI-surface unlock` (flow completes, server-dependent feature unverified) / `[OK] feature-level unlock` (the only externally-reportable done state). State the current tier explicitly in any progress report.
    - **Byte-level handling of ciphertext/keys/device codes**: any long redundancy-free payload (ciphertext, base64, key, IV, device code, license key, token) must be copied byte-for-byte from a capture record or file, or extracted programmatically -- never retyped from memory or across turns. One real run dropped an `F` retyping a code by hand, misaligning base64 length -> AES parse exception -> falsely diagnosed as "data corrupted," wasting a debugging round.
   - **Generalizing to tool-behavior assumptions**: the same passive-observe->verify->act principle applies to any "how will this MITM proxy/sandbox/hook framework handle X" judgment a later step depends on -- test it with one independent minimal request first, never take it from a tutorial or intuition. Verification is cheap (one command); being wrong is expensive (one real run assumed a MITM tool mints certs from the SNI hostname per textbook behavior, when it actually copied the upstream SAN -- one `openssl s_client -proxy` call would have caught this instantly, but 3 rounds of config changes happened first on the wrong assumption).

20. **Once app-layer encryption is confirmed, hook every candidate crypto library at once, don't guess incrementally; "parameter is fixed" needs >=2 independent samples**: common combos by frequency -- `crypto-js` / Node's native `crypto` / `jsencrypt`/`node-forge` (RSA) / built-in TLS. Hook all their encrypt/decrypt entry points together once confirmed, not one library then add more after failure -- request encryption and response decryption can genuinely use different libraries (one real case: crypto-js for requests, native crypto for response decryption; incremental guessing cost an extra repackage round). Monkey-patch at the JS layer for Node/Electron (`require('crypto')`/`crypto-js`/`jsencrypt`); reusable observer in `templates/mitm-observer.js` (injected in the target's own Node context, not Frida `-l`). Any "fixed parameter" conclusion needs >=2 independent samples first -- figure out which fields change (IV/nonce/timestamp, and its protocol position) before choosing a forgery strategy. Concluding "fixed key" from one sample is a high-risk misjudgment.

21. **Edit->repack->restart loop: zero tolerance for the process not exiting + mandatory integrity check after repacking + one layer per round** (applies to any archive/installer/compiled artifact, not just asar):
    - **Before packaging**: confirm the target process has fully exited via the process list, not a grep on your own output. A locked `.node`/`.dll` can make many packagers silently write a corrupted/truncated file while still exiting 0.
    - **After packaging**: re-extract key files and verify the change took effect and the size/structure is sane -- never trust exit code 0 alone.
    - **Electron asar**: use official `@electron/asar` (not the old `asar` package); modern Electron often has an integrity fuse that can detect repackaging and refuse to launch -- check for it first; if present, switch to a runtime hook (Frida) instead.
    - **One layer per round**: auth bypasses often span render layer / main-process-proxy layer / protocol-forgery layer. Changing two layers at once means an unexpected result can't be attributed to either -- verify each layer independently, then combine.
    - **Don't miss compiler-generated implicit files**: exit code 0 only proves the packager finished, not that every runtime-needed file is present -- Java `Outer$1.class`, Kotlin companion objects, etc. are easily hand-omitted. Enumerate the actual compiled-output directory (`Get-ChildItem -Recurse *.class`) rather than hand-writing a file list.

22. **DLL hijacking/search-order abuse is a Windows-specific, independent bypass route -- don't fixate only on networking and memory hooks**: a native exe searches for dependency DLLs in a fixed order (app dir -> System32 -> PATH). If it loads a non-system DLL from its own directory without signature/absolute-path verification, drop a same-named proxy DLL (forwards real functions + injects your logic) to hijack the authorization decision or an export's return value -- no main-exe edit, no unpacking needed. Locate hijackable points via Procmon's `NAME NOT FOUND`/`PATH NOT FOUND` on DLL loads during Stage 2, or check the import table for non-system DLLs loaded from the app directory. Verify attribution/signature per Rule 12 -- signature-checked DLLs are a dead end here.

23. **Score injection/observation channels first, then verify they actually work, switch after 2 zero-evidence attempts (isomorphic to Rule 14)**:
    - **List and score candidates first, don't grab whichever's closest (echoes Rule 16)**. For Electron/Node-on-Windows, rank by anti-injection resistance / proximity to the decision point: render-layer DevTools console >= Electron-as-Node offline invocation (`ELECTRON_RUN_AS_NODE=1`, no GUI, immune to main-process anti-injection) >= `--inspect`/Frida attach to a live process > main-process `NODE_OPTIONS=--require` (easily fuse-blocked -- list as a candidate, not the default) > system-proxy capture (only once confirmed proxied).
    - **"Script loaded" != "channel works"**: only counts once you have real evidence (hook log, real DevTools state read, offline call matching expectations) while the target is fully running. A process that exits instantly, has no GUI, or gets single-instance-locked writing "the first log line" is always a false positive.
    - **Env-var injection: land a diagnostic before claiming success**: write the variable's actual value + the target's full path to a diagnostic file before launch, distinguishing (a) never set, (b) set but ignored (fuse/anti-injection), (c) target relaunched itself without the variable.
    - **2 zero-evidence attempts on a fully-running target = structurally dead -- switch immediately**, don't retry the same channel a 3rd time.
    - **A channel getting blocked is itself hardening evidence** (Rule 6) -- write it straight into Stage 5.

24. **Any user-facing artifact must be pure ASCII; a target's non-ASCII name is only ever a quoted string**:
    - `.cmd`/`.bat` files: zero Chinese anywhere (comments/echo/prompts) -- Windows console defaults to GBK and Chinese garbles/crashes on double-click.
    - Artifact filenames and log/diagnostic paths: pure ASCII (e.g. `%TEMP%\<ascii>.log`).
    - A target's non-ASCII exe name/path: only as a PowerShell quoted string or via `Get-ChildItem`'s `.FullName` -- never in a bare `.cmd` line/comment/echo.
    - Applies beyond `.cmd`/`.bat`: any path parameter passed to a runtime component (a JVM argfile, `-javaagent:`, an env-var path) can break at that component's own encoding layer even outside cmd/GBK parsing -- copy/symlink non-ASCII paths to pure-ASCII first, as a standing default for the rest of that analysis. Also: if a parameter change produced no error but also no visible behavior change, suspect it never reached the target process (shell escaping can silently swallow a separator) -- confirm with a minimal command before running the full target.

25. **Batch-test independent read-only/harness-isolated sub-hypotheses in parallel, don't edit-and-rerun one at a time; side-effecting or user-action steps stay serial + consented**: after Stage 2.5's route table is scored, if any of these apply, test them all in one pass inside the same harness rather than one change at a time:
    - Multiple independent candidates under the same route (candidate keys, response formats, gate locations, signature params) -- loop over them in the script instead of changing an env var and rerunning each time.
    - 2-3 routes scoring close together -- gather read-only evidence for several at once (reading files, offline harness, curling a known endpoint) before committing.
    - Two mechanisms, usable together: (a) an in-process loop when candidates are "same logic, different params"; (b) parallel sub-agents when candidates are "genuinely different routes needing different files/checks, independent and stateless relative to each other."
    - **Precondition boundary (non-negotiable, echoes Rules 5/8/9)**: strictly read-only or harness-process-isolated exploration only. Anything requiring real user GUI action, or with side effects (modifying mitm.js, a target file), stays one-at-a-time with consent per Rule 5 -- parallelism never extends to side-effecting steps, and never becomes an excuse to batch multiple pending changes to the user or ask less often. A sub-agent doing anything side-effecting must likewise stop and ask.
    - **Convergence**: after batch testing, carry forward only evidence-supported conclusions -- log the rest (with disproving evidence) into the memory log (Rule 7); don't turn an unverified guess into a conclusion just because batch testing surfaced a lot of information (Rule 6).

26. **Dynamic->static stop-loss: a stalled live-debugging loop (or a target already plaintext in memory) means dump the module + go to IDA -- do NOT add a 3rd breakpoint (symmetric to Rule 14's dynamic-internal stop-loss)**: the skill was structurally biased "dynamic-first, static-late" -- it treated IDA (4A) as the fallback *after* dynamic fails, and had no rule forcing the reverse switch. One real run burned 20+ rounds of runtime breakpoints on an already-decrypted, obfuscated, auto-re-verifying target before anyone thought to dump+IDA. This rule closes that hole.
    - **Mandatory switch triggers (any ONE -> stop live-debugging, dump the decrypted module, go to IDA static+xref)**:
      - Same analysis goal (locate a function/constant/decision point) sees **2 consecutive runtime-anchor attempts with zero progress** -- don't place a 3rd breakpoint, switch the *method*, not the anchor.
      - **Junk code / linear-disassembly misalignment**: `EB 01`/`EB 02` skip-bytes, overlapping instructions, fake `far jmp`, or disassembly contradicting known control flow. Linear disassembly (MCP/x64dbg `disassembly_at`) *will* misread these -- IDA's recursive-descent + flow analysis is the fix. This is a high-priority static trigger on its own (doesn't need to wait for the 2-attempt count).
      - **Event storm**: a breakpoint on a UI-related API (window-proc/dispatcher/`GetWindowTextLength`/timer) fires hundreds of times without user action (one real run hit `hit_count=1094`, all noise), drowning the one hit you want. Static analysis is frequency-independent -- switch.
      - **Decision/display decoupling**: what you keep catching is the *error-display/consumer* side (stack bottom is the message pump / `OnCmdMsg` / `WindowProc`), and the check that *produced* it is on a different call stack (async `PostMessage`/custom message/command code). Stop chasing the popup; static-xref the decision that produces the error string instead.
      - **No xref in x64dbg** (reflectively-loaded / unregistered module): x64dbg can't build xrefs for it -- dump->IDA is the only way to get "who references this".
    - **Memory-plaintext = static's best moment**: once a native module is confirmed decrypted in memory (shell self-decrypt / reflective load / manual dump), **dump-to-file -> IDA is the default next step, not "keep going dynamic".** Memory plaintext + IDA xref = shortest path. Live breakpoints are for *observing runtime data* (decrypted plaintext, network content, confirming a hit landed -- Rule 4), **never for finding static facts**.
    - **Rule 14 vs Rule 26 -- pick by what you need**: need the **runtime execution flow / just to bypass** virtualized-or-flattened code -> Frida Stalker (Rule 14). Need a **static fact** -- a precise constant, branch condition, algorithm structure, or the origin of a string/behavior -> IDA recursive-descent + xref (Rule 26). Both share the same "stop hand-single-stepping / stop linear reading" instinct; they differ only in the deliverable.
    - **Task-nature routing (decide the tool by what the task IS, before touching either)**:

      | Task nature | First choice |
      |---|---|
      | Find a precise constant / comparison value / branch condition / algorithm shape | **Static (IDA + xref)** |
      | Observe runtime data / post-decryption plaintext / network content | Dynamic (hook/breakpoint) |
      | Confirm a decision point actually executes | Dynamic (breakpoint hit, Rule 4) |
      | Locate "which code produced this string / behavior" | **Static (xref that string/API)** |

    - **Per-strategy attempt budget = 2, logged as a triple**: give every strategy a **default budget of 2 attempts** and record `[strategy - attempt count - conclusion]` explicitly in the memory log (Rule 7). Hitting the budget forces a *method-level* re-evaluation (switch static/tool/target-layer), not another tactical breakpoint swap. This makes "just try one more breakpoint" impossible to loop on forever.
    - **Coherence with Rule 4**: IDA locates the static fact; marking a critical check `[OK]` still needs the user to personally witness the runtime bypass succeed. Static-first shortens the path to the fact -- it never replaces the runtime confirmation at the delivery moment.
    - **Mantra**: chase the *decision that produces the error*, not the *error popup*. Plaintext-in-memory + obfuscated + hunting a precise decision point = dump first, IDA second, don't play whack-a-mole in the live process. Two dynamic tries with no progress = change the method layer, not the 3rd breakpoint.

27. **VM'd auth core = attack it at its boundary, don't flee it -- once the verdict is localized to a VMProtect/Themida/encrypted region, going around it is a banned retreat**: this rule exists because "the VM is hard" is the most seductive excuse to abandon a *confirmed* location and wander off to a softer-looking target that isn't actually where the decision lives. Once static/dynamic evidence shows the authorization verdict is computed inside a virtualized/encrypted core -- an indirect call into a VMProtect/Themida/obfuscated region, or a verdict landing in an encrypted global -- the decision **provably lives there and nowhere else**, so any route that doesn't touch that boundary is by definition attacking the wrong place. The skill kept letting "hard core" reroute the analysis to fake-server / registry-diff / network-capture, all of which fail precisely *because* the real verdict never traverses them.
    - **The mandate**: defeat it **at its boundary** -- the interface between clean (non-virtualized) code and the VM'd evaluator. That boundary is where the plaintext verdict is necessarily exposed, because the surrounding program has to consume it in the clear.
    - **Sanctioned tactics, in order**:
      - **(a) Hook the boundary call** -- the last clean instruction that invokes the VM'd evaluator and receives its return. First **OBSERVE** the return/verdict black-box across >=2 states (unactivated vs activated, or two different inputs) to learn what "authorized" looks like (Rule 19's >=2 samples), **then FORCE** it: patch the return register, or flip the consuming `test`/`jz`, to the activated value.
      - **(b) Verdict cached to an encrypted global** -> don't try to decrypt the global offline; resolve it **at the consuming site**, where it is decrypted into a register for use, and force that register / the branch that reads it.
      - **(c) Many consumers, one verdict** -> find the single boundary evaluator that every nag/gate/feature-check calls, and force *that one*, rather than patching each consumer site individually (whack-a-mole across dozens of gates).
      - **(d) Boundary itself fully virtualized end-to-end** (no clean consuming instruction anywhere -- the verdict is produced and consumed entirely inside the VM) -> only now does Frida Stalker tracing / devirtualization of **that one function** become necessary (escalation per Rule 14).
    - **Banned retreats** (all are "the VM is hard so I'll go around it" fallacies, forbidden the moment the verdict is localized to the core): fleeing to fake-server/replay, to registry-state diffing, to "just capture the startup network verdict." Each is banned **only as a detour to avoid the VM** -- if one of them is *independently confirmed* to be the actual verdict SOURCE (e.g. the server genuinely returns the entitlement and the client merely displays it -- a server data-gate per `auth-arch-classify.md`), then it's the correct route, not a retreat. The test is intent + evidence: are you going there because that's where the decision provably is, or because the VM scared you off the place it provably is?
    - **[VERIFY BEFORE COMMIT -- this rule only binds AFTER the premise is proven, not on a hunch that "the core looks scary"]**: before committing to the boundary-attack mandate, you must have **hard evidence the verdict actually lives in the VM'd core**, not just that a VM exists somewhere in the binary. Sufficient evidence, any one: (a) a traced indirect `call`/`jmp` landing inside the virtualized/encrypted range *on the auth path*; (b) the verdict-consuming `test`/`jz` reads a global/register whose producer is inside that range; (c) xref shows every gate funnels into one evaluator sitting in the protected region. **"The exe is VMProtect-packed" alone is NOT this evidence** -- a VM'd *shell* can still leave the *auth check* in plain code (a real trap: assuming the check is in the VM because the packer is, and ignoring a plaintext boolean gate elsewhere). If you can't produce (a)/(b)/(c), the premise isn't met -- treat auth location as still-open and keep localizing (Rule 26), don't invoke this rule yet.
    - **[MISJUDGE RECOVERY -- 2x-stall may mean "wrong premise", not "need a heavier tool"]**: the sanctioned exit is "boundary hook stalled 2x with zero evidence" (Rule 23's budget) -- but before escalating to Stalker/devirt of that function (Rule 14), **first re-test the premise**: is the verdict *actually* in the VM, or did I misjudge (b/c above)? Cheap re-checks: is there a plaintext branch/boolean/string-referenced check elsewhere the xref missed? did the "boundary" I hooked actually sit on the auth path, or on an unrelated VM'd routine? Only if the premise re-holds does escalation to Stalker/devirt apply; if it doesn't, the correct move is back to Rule 26 localization, not a heavier attack on the wrong spot. Escalation is **harder-but-correct**, never harder-on-a-wrong-target.
    - **Coherence**: this is the Stage-2.5 veto (Rule 16) made into an active mandate -- Rule 16 says "VM protector vetoes fake-the-server"; Rule 27 says what to do *instead* (attack the boundary) and forbids the sideways escape. Marking `[OK]` still requires the user to witness the forced verdict actually unlock the real feature (Rule 6).

28. **Control-ownership fork -- decide "Hook vs capture" by "can I inject into this process," BEFORE any default action**: this is the single most upstream branch of the whole pipeline, and it must be answered before Fast-path step 1 or Stage 2.5 scoring -- not discovered after a wasted capture round. The skill's old default ("open Reqable + system proxy, walk one login") silently assumed system-proxy capture is always the cheapest first move. For a **local rich client** (Python/Qt/Electron/.NET packaged, running on a machine we control) that is frequently false: the target often ships its **own network stack** (Cronet `sscronet.pyd` / static BoringSSL / Go `net` / Qt Network / some .NET configs) that **ignores the system proxy outright**, or uses cert pinning / loopback / raw sockets -- so proxy capture catches **nothing**, and that is the **norm for this class of target, not the exception**. Chasing it (open proxy -> empty -> diagnose why -> TUN/Proxifier -> defeat pinning) is a long detour that is entirely skippable when we own the machine and Frida/x64dbg work.
    - **The fork (ask this first, one question, answerable from Stage 0/1 facts)**: **"Can I inject code into the target process?"**
      - **Yes** (local process we own, Frida/x64dbg injects, not PPL/anti-injection-locked) -> **in-process Hook is the first-choice primary route**: hook the target's *own* SSL / network / decision / verify functions to read plaintext *before encryption* (SSL `_ex` clause per recipes §4.9). Capture drops to a **parallel secondary corroboration**, never the thing you wait on first.
      - **No** (mobile / remote / PPL-protected / injection refused / genuinely a black-box network device speaking standard HTTP proxy) -> **then** capture / fake-server / network-side moves up and is first.
        - **[STOP + HANDOFF -- capture is always the user's action, and you pause for it (Rules 8/9)]**: when capture is the route, **stop the session and hand it to the user** -- tell them to start the interceptor + proxy before opening the target, walk one auth flow, and **report whether records appeared**. Then **wait**; never proceed on the assumption that records exist, never capture on their behalf.
        - **[EMPTY CAPTURE = YOUR CUE TO HANDLE IT, not to give up]**: capture is not "open a system proxy and walk a login" -- that catches almost nothing (real clients ship Cronet/BoringSSL/Go/Qt stacks that ignore the system proxy and/or pin certs). So when the user reports an empty capture, **that's the setup gap you now resolve** (drive the plan, user executes -- Rules 8/9): (1) **force the traffic into the interceptor** -- Proxifier / TUN mode per-app forced-forward (`tool-registry.md Sec.4.5`, `env-recon.md` I-Addendum); (2) **install + trust the interceptor's CA cert** for HTTPS MITM, and **defeat pinning first** if present (Frida-unpin, then return to the proxy). Verify decryption really happened (`openssl s_client -proxy`, check the issuer is the MITM CA not the real CA -- `env-recon.md`). Loopback/raw-socket can't be proxied at all -> local hook. Empty capture is a setup gap, not proof there's no traffic -- and if the target is actually locally injectable, empty capture means you were on the wrong branch: go hook the pre-encryption plaintext instead.
    - **Why it's a separate rule, not just Rule 16 scoring**: Rule 16's table scored feasibility/difficulty but treated "do we own the process" as *implicit*, so the "just open a proxy" habit kept overriding it. Making it an **explicit, top-priority fork** stops that. It does not remove the transport-layer recon (env-recon §I) -- it *front-loads* it: the "which network DLL" pre-judgment (`scan.ps1` step [4]) happens at Stage 1 scan time, so "system-proxy capture" can be scored dead **before** the user is asked to walk a login, not after.
    - **One-line principle (mirror of this in SKILL.md Fast path)**: *Local rich client + can inject = Hook the process for pre-encryption plaintext first; don't go fight the system proxy. "Capture came back empty" is not a "should I add Proxifier/TUN" question -- first ask: this machine is mine, why am I not just hooking its own SSL/network/decision functions? Capture is first only when the process is out of reach.*
    - **[DON'T GUESS -- prove the fork with a cheap read-only test, per Rule 19's verify-cheaply principle]**: "can I inject?" is answerable by a **~30s read-only probe**, not a hunch. Do it (read-only, needs no consent -- Rule 25): a minimal Frida attach that only enumerates modules (`frida -n <proc> -e "Process.enumerateModules()"` or the equivalent one-liner) / x64dbg attach that just lists modules. **Success (modules listed) = injectable -> Hook route confirmed.** **Failure with a specific signal = the fork's "No" branch, now evidence-backed**: `ECONNREFUSED`/attach-refused/`access denied`/PPL error/frida-server absent. Don't spend the whole Hook route on an *assumed* "yes" -- spend 30s proving it. Same for the network-stack half: `scan.ps1` step [4] is the pre-judgment, but if it's inconclusive, one minimal `openssl s_client -proxy` / a single captured request confirms "does proxy see anything" before you commit.
    - **[MISJUDGE RECOVERY -- committed to a branch + 2x zero-evidence = re-question the FORK, not just the tactic]**: if you chose **Hook** and got 2 zero-evidence attempts (Rule 23 budget), before grinding a 3rd hook point, re-test the fork itself: is injection *silently* half-blocked (attaches but hooks never fire = anti-hook/PPL-lite -> this is actually the "No" branch)? did I misread the network stack (assumed self-contained, but it's plain WinINet and capture *would* have worked)? Flip to the other branch **on evidence**, not on frustration. Symmetric for the capture branch: 2x empty capture on a local target we own = stop diagnosing the proxy, go back and prove injectability (the fork probably should have been "yes"). The recovery is *switch the fork verdict when the evidence contradicts it*, never "try the same branch harder".
    - **Boundary (no conflict with existing rules)**: this fork sets *route priority*; it never relaxes Rules 5/8/9 -- the user still opens tools and drives the target, Hooks that change flow still need consent, and "witnessed bypass" (Rule 6) is still the only `[OK]`. It also doesn't ban capture -- passive capture in parallel is exactly Rule 19's field-dictionary source; it just stops capture being the *blocking first step* for injectable local targets.

29. **[IRON] No `ddgs` installed = NO web search, period**: every web lookup MUST go through the **`ddgs`** Python library (`pip install ddgs` -- the renamed `duckduckgo_search`; a no-API-key multi-engine metasearch lib). Before any search, confirm `ddgs` is importable; if not, **STOP and tell the user "missing ddgs, run `pip install ddgs`"** and wait (Rule 5 -- user installs, you never auto-install). **Banned**: the flaky built-in `web_search` tool, and `curl`/PowerShell scraping of Google/Bing/DuckDuckGo HTML (real pain this session: web_search returned inconsistent/degraded results and curl-to-search-engine kept failing TLS/JS). No `ddgs` -> no search -> say so and stop, never fall back to the banned channels. Still route by destination (Rule 2): `ddgs` for overseas; domestic 看雪/52pojie stay direct via `curl.exe`. Usage: `ddgs text -q "<query>" -m <N>` (CLI) or `from ddgs import DDGS; DDGS().text("<query>", max_results=N)` (API).

30. **[IRON] Packed target = IDA is FORBIDDEN until unpacked to plaintext**: the moment `scan.ps1`/Exeinfo PE confirms the target (or the module you're attacking) is packed/protected (Safengine/SProtect/VMProtect/Themida/any commercial shell), **do NOT open it in IDA / call any `mcp__ida__*`**. Reason (paid for repeatedly this session): a packed binary's real code is encrypted/virtualized/absent statically -- IDA sees stubs, zero-filled function bodies, or unanalyzable regions ("no function", `define_code` fails); grinding IDA on it is a proven dead end and pure time-waste. **The only sanctioned IDA use is on a plaintext dump**: first defeat the shell (per Rule 3 search -> unpack/dump via ScyllaHide+x64dbg dump_module, or the shell's documented method) to get an unpacked module, THEN IDA is allowed on that dumped plaintext. Before unpacking, to inspect logic use: runtime-decrypted memory dump + capstone disassembly, proxy-DLL boundary logging, or Frida read-only introspection -- never IDA on the still-packed file. This is the active form of Rule 26's "memory-plaintext = static's best moment": static (IDA) is powerful, but ONLY after the bytes are actually plaintext.
